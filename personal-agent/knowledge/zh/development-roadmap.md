# 开发路线图

## 我们实现了什么

项目现在把三类规划产物分开：

- `PLAN.md` 保留已经完成的 MVP 设计与里程碑。
- `ROADMAP.md` 按依赖关系和完成门槛排列 MVP 之后的阶段。
- `TODO.md` 保存有价值但尚未排序的能力想法。

路线图先处理可复现基线和任务正确性评测，再依次推进 Skill Pack 可移植性、类型化执行、对话上下文、联网、检索和生产可靠性。

## 在本项目中如何工作

每个路线图阶段都声明 deliverables、完成门槛和学习重点。完成门槛用于阻止后面的功能在前置安全或评测基础缺失时成为默认开发主线。

能力变更仍遵守现有知识库规则：同一次变更必须用中英文解释实现方式、其他方案、优缺点、风险和评测方法。

## 其他常见方案

**扁平 backlog**：
把所有想法放在同一个 TODO 中。维护简单，但看不出依赖关系，容易让更吸引人的功能挤压基础工作。

**日期驱动路线图**：
给功能指定日历目标。适合多人协调，但对于单 Owner 的学习项目，开发速度取决于每个阶段暴露的问题，日期容易产生虚假的确定性。

**框架驱动路线图**：
先采用框架，再按框架的能力模型推进。部分集成会更快，但学习路径和架构也容易被框架术语绑定。

**能力门槛**：
只有可观察的完成标准通过后才进入下一阶段。本项目采用这种方式，让顺序由证据决定。

## 为什么选择当前方案

MVP 已经有不少可见能力，但最薄弱的部分是证明任务结果真的正确。因此 Evaluation 必须排在联网和检索之前。Skill 可移植性排在脚本执行之前，是为了先明确能力来源和权限边界，再增加执行能力。

在学习密集的阶段继续保留 first-party loop。只有实际测得的编排、handoff 或 retrieval 复杂度足以证明迁移价值时，才重新评估框架。

Task Evaluation V2 现已完成：结构化 checks、证据维度、Golden Task Runs 和带审计记录的人工 verdict override 已满足 Phase 2 gate。因此下一条默认工作流进入 Ability Bridge 和有顺序的 Skill sources。

## 优势

- 明确展示依赖关系和停止条件。
- 防止评测与安全工作被新增功能挤压。
- 保持已完成 MVP 历史稳定。
- 保留 backlog 想法，同时不假装它们已经排期。
- 每个阶段都有明确的 Agent 学习目标。

## 劣势与风险

- Gate-based 阶段不会承诺具体日历日期。
- 真实使用暴露出更好证据后，需要维护完成标准。
- 紧急小修复可能暂时跨越阶段边界。
- 如果没有可执行验证，只靠手工把 gate 标记完成，路线图会变成形式主义。

## 如何评测

路线图质量由证据判断，而不是由文档是否存在判断：

- 当前阶段包含可度量的完成门槛，
- 每个被提升的能力都有 focused tests 和端到端测试，
- 延后工作仍保存在 `TODO.md`，
- 中英文知识文档保持同步，
- 默认下一项工作始终是最早尚未完成的阶段。
